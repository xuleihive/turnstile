# WorkBuddy 用量监控实测

## 范围与方法

- 时间：2026-10-12 01:44–01:46，Asia/Shanghai。
- 使用本机 WorkBuddy 5.8.0，独立新建任务；模型为现有 AIGateway / cc-switch / gpt-6.1-sol。未改动 magpie、插件、Agent 配置或线上服务配置。
- 连续发送 A、B、C 三条带唯一标记的简短算术请求，明确禁止工具、联网和文件操作。
- 测试前 Azure PostgreSQL 状态为 Ready。使用已认证的平台请求 API，以 active + unattributed 查询；约每 0.5 秒轮询一次，实际间隔还包含 HTTP 耗时。
- 本地 magpie usage.jsonl 以 0.1 秒间隔观察新增记录；只保留本次 WorkBuddy / AIGateway 用量元数据。独立读取本次 WorkBuddy 会话的 providerData.usage，与平台详情逐条核对。
- 完成时间使用 magpie 请求起始时间加 ms。API 延迟指完成到第一次查询可见的时间，不是数据库精确写入时间。页面保持可见，不点击刷新；B、C 页面观测间隔约 0.2–0.3 秒。
- 原始记录、采样脚本、截图仅保存在私有临时目录，不纳入 Git；不包含 API Key 或登录凭据。

## 延迟解释与边界

1. 这不是推送式实时监控。APIM → Event Hub → Telemetry → PostgreSQL 是异步链路，页面另外每 10 秒轮询一次，后台标签页不轮询。
2. B、C 的数据查询可见延迟约 0.5 秒；A 首轮两条请求延迟约 10–12 秒且在同一次查询中出现。实测证明异步链路存在波动，但本次未采集函数冷启动及 Event Hub 分区处理日志，不能把首轮延迟确定归因于冷启动或批处理。
3. B、C 的页面自动可见延迟分别约 1.4 秒和 8.5 秒，与 10 秒刷新周期相符。A 页面采样中断，只能提供观测区间，不能将 26 秒当成精确测量值。
4. 通用流式请求仍可能先以不完整用量入库，再通过 reconcile_stream_usage 每 10 分钟补齐；当前默认安全滞后为 6 分钟，且 Azure Monitor 日志还存在摄取延迟。不能将本次 Event Hub 完整用量样本的秒级延迟推广为所有请求的 SLA。
5. Token 数量核对通过；estimated_cost 是按平台价格估算的费用，本次未与 Azure 实际账单对账。
6. API 的 timestamp 是请求时间，不能据此反推出精确入库时间。本次使用客户端轮询的首次可见时间，因此 API 延迟包含约一个轮询间隔和网络耗时；小样本不构成 P95/P99 指标。

## 结论

已部署修复下，本次 WorkBuddy 的调用计数、输入/缓存/输出 Token 数量及页面自动刷新均通过核对，没有发现需要再次修改部署的核心监控错误。后续如需严格测量链路各阶段延迟，应记录请求完成、事件发布、数据库写入三个独立时间戳；如需优化流式最终用量时效，应单独设计完整 usage 事件回传，而不是仅缩短页面刷新周期。
