# 插件 Roadmap

记录日期：2026-10-18。状态：**规划，尚未实现**。
本文件集中维护插件后续能力，不是发布记录、线上配置或开发授权。
现有行为见[插件设计](design.md)，已完成的 USD 结果见[验收记录](usd-installation.md)。

## 上游 TPM/RPM 感知与请求调度

### 目标

在平台模型管理中读取真实上游部署限额，随插件下载及模型刷新传递，
使用宿主支持的接口提供安全默认值，减少 WorkBuddy 等客户端的突发请求。
不将并发、RPM、单次上下文长度与 TPM 混为一谈，不宣称本地调度能够扩大上游容量。

### 当前能力基线

以下依据记录日的平台源码及本地核对的 Magpie 0.1.1279；实施前重新核对宿主版本和协议。

| 能力 | 当前状态 | 规划边界 |
| --- | --- | --- |
| 模型管理读取部署 TPM/RPM | 模型契约尚未保存和展示这两项上游部署限额 | 增加管理面只读采集、资源映射和来源/时效信息 |
| 下载和刷新传递限额 | 双版插件当前不携带速率限制 | 扩展可选、版本化的目录元数据，兼容旧包和未知值 |
| 插件声明默认并发 | Magpie 支持 `auth.maxConcurrency` 或 `package.json` 的 `magpie.maxConcurrency`；本插件未声明 | 可在不修改 Magpie 源码的情况下接入，用户显式设置优先 |
| Magpie 原生 RPM | 有供应商/账号级手动 `maxRPM`，插件声明接口未接入该字段 | 不能仅在插件配置中填写同名字段就声称自动登记成功 |
| Magpie 原生 TPM | 未发现模型级 TPM 调度字段 | 需要独立调度实现或未来宿主协议支持，不复用 `limit.context/output` |

Magpie 的并发和 RPM 按账号/Key 控制，不是按模型部署汇总。
同一插件供应商下的多个模型可能共用本地限制，而同一上游部署也可能被多个插件账号共用。

### 分阶段规划

| 阶段 | 计划能力 | 验收条件 |
| --- | --- | --- |
| P0：限额采集与展示 | 平台通过 Azure 管理面读取对应 Foundry 部署的 `properties.rateLimits`；显示 TPM/RPM、来源及读取时间 | 精确匹配部署；保留原始计数周期；读取失败/缺权限/过期不显示成无限制；不修改 Azure 限额 |
| P1：插件分发与默认并发 | 双版下载包及模型刷新携带版本化限额；通过正式插件字段声明默认并发 | 新旧契约兼容；用户覆盖值保留；宿主实际采用默认值，不能只检查导出 JSON；不声称原生 TPM/RPM 已自动登记 |
| P2：可选本地调度 | 单独评审插件 `fetch` 层按部署分组的 RPM/Token 估算、排队、取消及 429 退避 | 有限队列、等待与客户端超时匹配；不自动重放未知结果；单请求超过可处理上限时不无限排队；不影响其他供应商 |
| P3：跨客户端协调 | 另行设计平台侧按部署共享的请求调度，覆盖多用户/多账号共用容量 | 明确实例间协调、限额分配、重启恢复和故障策略；不得绕过或改写现有预算、鉴权及 APIM 管控 |
| 宿主协同：原生 RPM/TPM | 若未来要求自动登记到 Magpie 原生设置，单独核对并推动正式插件/配置接口 | 明确支持版本、用户覆盖语义及真实宿主测试；未获得支持前标为不可用，不直接改宿主配置文件 |

P0/P1 为优先候选；P2/P3 和宿主协同不是本轮已承诺实现。
每阶段实施前再确定详细设计、变更范围与测试计划，不在下载时隐式启用新调度或改线上容量。

### 数据与权限设计原则

- **部署维度**：按资源、部署、区域及限额作用域关联模型，不能只按 `grok-4.7` 等显示名归并。
  多模型共用部署、同名不同部署、后端池和故障切换分别建模，不能简单相加或把容量当作个人独享。
- **区分限制来源**：Foundry 部署上限、平台应用/订阅 TPM、个人预算及客户端偏好是不同约束。
  实际请求应满足所有适用约束，不用一个来源覆盖其他来源。
- **保留计数周期**：采集 Token/Request 的 count、renewal period 与来源；必要时提供每分钟展示值，
  但不能用归一化结果丢弃较短窗口或突发约束。部署 capacity 和区域可分配 quota 不等于同一限额。
- **只读权限**：平台需要对应 Azure 资源的管理面只读权限及明确资源映射；不能假定推理 Key 就能读 ARM。
  凭据只留服务器，不下发 Azure 管理令牌、订阅 Key 或完整配置给插件。
- **时效与未知**：记录读取时间、来源、状态、版本及过期策略；缓存/定时刷新/手动刷新按需设计，
  不在每次模型调用或下载中串行查询 ARM。失败不填零、不冒充实时剩余额度。
- **分发兼容**：插件可以携带脱敏的部署分组标识、限额快照及客户端建议；最终字段名须在实施时锁定契约。
  新字段可选，旧插件忽略新增元数据；已安装包后续通过模型刷新更新，不要求每次重新下载。

### 宿主登记与用户控制

1. 优先使用 Magpie 已公开的并发声明；`auth.maxConcurrency` 优先于包声明，用户显式限制优先于插件默认值。
2. 默认并发是可解释的客户端建议，不能仅由 TPM/RPM 精确推导；不得把当前 Grok 限额写成所有模型的固定默认值。
3. 当前不把 `auth.maxRPM`、`magpie.maxRPM` 或模型 `limit.tpm` 视为已经支持的宿主接口。
4. 不直接修改 `providers.json` 或宿主用量历史，不覆盖用户手工 RPM/并发，也不靠私有 GUI 接口模拟注册。
5. “限额信息已刷新”“插件调度已启用”“宿主已采用设置”分别验证和展示，不能以文件包含字段替代运行时证明。

### 调度与财务边界

- RPM 只限制次数，并发只限制同时在途数；Token 调度还需考虑完整上下文、工具定义、输出上界及提供方计数规则。
  不用付费 Token 数、缓存折扣或月度 USD 余额直接换算 TPM。
- 本地调度是辅助措施，不提供跨机器共享容量保证；全局治理应由平台和上游限额继续兜底。
- 请求取消、流开始、超时及重试必须有明确状态；已发出但结果未知的请求不得自动重放或释放其财务预留。
- 遵守适用的 `Retry-After`，设有界队列与等待上限，不让客户端先超时后继续后台发出付费请求。
- 普通 429、流内错误、排队拒绝与预算拒绝应可区分；本路线图不把现有平台 200/流内失败问题当成已修复。
- 不修改客户端源码、现有鉴权、模型授权、预算协议、已应用迁移或历史消费；如需持久化结构变更，另做迁移评审。

### 实施验收清单

- 管理面缺权限、缺字段、不同计数周期、过期快照、区域/部署重名、共享部署及后端池映射。
- 用户版/订阅版下载、旧配置加载、模型刷新、默认并发实际生效及用户手动覆盖。
- 多账号共享、本地多进程、取消、重启、队列满、超时、`Retry-After`、流内失败和未知结果不重放。
- 原 Token/USD 预算、身份、订阅绑定、模型访问与其他供应商回归；不将隔离调度测试当作真实云容量验收。
- 先使用本地模拟上游；真实推理和云限额调整必须另行获批，不沿用已结束任务的测试费用授权。
